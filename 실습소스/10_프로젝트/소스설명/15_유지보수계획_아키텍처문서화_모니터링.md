# 15. 유지보수 계획 · 아키텍처 · 모니터링 — 소스 설명

대응 노트북: `notebooks/15_유지보수계획_아키텍처문서화_모니터링.ipynb`

## 한눈에 보기

코드뿐 아니라 **운영 문서**를 만듭니다.  
시스템이 “어떻게 생겼고, 무엇을 감시하고, 누가 언제 점검하는지”를 남깁니다.

주요 산출물:

| 파일 | 내용 |
|------|------|
| `docs/architecture_doc.json` | 계층·컴포넌트·의존성 |
| `docs/runbook_incident.md` | 장애 대응 절차 |
| `outputs/maintenance/` | 모니터링 계획, 점검 캘린더 등 |

## 초보자를 위한 용어 사전

| 용어 | 쉬운 설명 |
|------|-----------|
| **아키텍처 문서** | 시스템이 어떤 부품으로 어떻게 연결되는지 적은 설계 문서. |
| **C4 모델** | 시스템·컨테이너·컴포넌트·코드 수준으로 나누어 그리는 방법. |
| **모니터링** | 살아 있는지, 느린지, 에러가 나는지 숫자로 감시. |
| **알람** | 임계값을 넘으면 사람/챗봇에 알림. |
| **SRE 4대 황금 신호** | Latency, Traffic, Errors, Saturation. |
| **Runbook** | 장애 났을 때 따라 할 체크리스트형 대응 문서. |
| **유지보수 캘린더** | 모델 재학습, 센서 캘리브레이션 등 정기 작업 일정. |

## 계층 구조 (요약)

```text
Presentation (API/대시보드)
→ Application (WebService, LLM, Eval)
→ Domain (Vision, Sensor, Fusion, Pipeline)
→ Data (이미지, 센서, 피드백 JSON)
→ Infra (Edge GPU, AOI 라인)
```

## 모니터링 예시 메트릭

- API p95 지연, 에러율, 분당 요청 수
- GPU 사용률
- HIGH 리스크 비율, LLM 사람검토 비율
- 품질 게이트 실패 건수
- 피드백 정확도(7일)

## 왜 필요한가?

PoC는 노트북으로 끝나지만, 현장은 **밤에도 돌아가야** 합니다.  
문서와 알람이 없으면 장애 때 “어디를 보지?”부터 헤맵니다.
